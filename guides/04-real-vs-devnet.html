~15 min read · Verified against source · Companion to guides 01–03

The contracts don't run on a server — they run on Arbitrum, which means every node in that network holds the state and re-executes the transactions. What does run on servers is go-livepeer, a Go daemon that orchestrators and gateways operate. Your devnet kept the contracts and deleted the daemon — so every button you press is a job that a running program normally does for you, on a schedule, without asking.

CHAPTER 01 — WHERE THE CONTRACTS LIVE

Nobody's server, which is the entire point.

There is no machine you could point at and say "the Livepeer protocol runs there". The contracts are deployed to Arbitrum One, a layer-2 rollup: every Arbitrum node holds a copy of the state and re-executes every transaction, and the "protocol" is the agreed result of that. Arbitrum in turn posts its results down to Ethereum for security. Take any single machine offline and nothing changes.

What is server-shaped is the RPC endpoint — Infura, Alchemy, or your own Arbitrum node. That's a door into the network, not the place the logic lives. When the protocol repo's .env asks for an INFURA_KEY, it's asking which door to knock on.

Your devnet collapses all of that into one process. When you run the SETUP panel's first step, the entire "network" becomes a single Node program listening on 127.0.0.1:8545. That's the biggest simplification in the whole sandbox, and it's why stopping it erases everything.

"An RPC endpoint is a door into the network. It is not the room the protocol is standing in."

CHAPTER 02 — WHAT DOES RUN ON SERVERS

go-livepeer is the daemon your buttons replaced.

An orchestrator runs go-livepeer on a GPU box. A gateway runs the same binary in gateway mode. These are ordinary servers with ordinary IP addresses, and they do three jobs at once: move video, sign payments, and keep the on-chain side ticking.

That third job is the one your UI made you do by hand. Two files inside go-livepeer are, literally, the two buttons you've been pressing:

eth/roundinitializer.go   → client.InitializeRound()   // the INITIALIZE ROUND button
eth/rewardservice.go      → client.Reward()            // the CALL REWARD button

The round initializer subscribes to new blocks, works out when the next round begins, and calls initializeRound() the moment it's allowed to. The reward service loops every round and calls reward(). Neither asks anyone. When I said earlier that "on the real network a bot does it" — roundinitializer.go is that bot.

There's a detail worth stealing. Every orchestrator's initializer wants to open the round, and only the first one to land pays gas for it. So the code sleeps a random delay first, then re-checks whether someone else already did it:

if r.maxDelay > 0 {
    randDelay := time.Duration(rand.Int63n(int64(r.maxDelay)))
    time.Sleep(randDelay)

    if r.tw.LastSeenL1Block().Cmp(r.nextRoundStartL1Block) < 0 {
        glog.Infof("Round is already initialized, not initializing")
        return nil
    }
}

Jitter to avoid a thundering herd of orchestrators all burning gas on the same transaction. Your devnet has exactly one participant, so the whole problem disappears and the button always works.

CHAPTER 03 — HOW THE TWO REPOS MEET

One generated binding, and one string written on the blockchain.

The protocol repo and go-livepeer connect in two very concrete places, and neither is a network call.

First: generated code. The protocol repo compiles its contracts and exports their ABIs — that's the abi/ directory produced by hardhat-abi-exporter when you run yarn compile. go-livepeer runs abigen over those files to produce typed Go bindings:

//go:generate abigen --abi protocol/abi/BondingManager.json  --type BondingManager …
//go:generate abigen --abi protocol/abi/TicketBroker.json    --type TicketBroker …
//go:generate abigen --abi protocol/abi/RoundsManager.json   --type RoundsManager …
//go:generate abigen --abi protocol/abi/ServiceRegistry.json --type ServiceRegistry …

Ten contracts in total. So when the protocol changes a function signature, go-livepeer regenerates and recompiles against it. That's the coupling.

Second: a string on-chain. This is the elegant one, and the contract is sitting in your local deploy right now:

// contracts/ServiceRegistry.sol
function setServiceURI(string calldata _serviceURI) external {
    records[msg.sender].serviceURI = _serviceURI;
    emit ServiceURIUpdate(msg.sender, _serviceURI);
}

An orchestrator writes its own network address onto the blockchain. That single string is the whole bridge between a staked on-chain identity and a physical machine that can encode video.

I told you earlier that go-livepeer's discovery reads that registry. That was imprecise, and the real design is better. Gateways don't query the chain per request — a watcher subscribes to ServiceURIUpdate events and writes each one into a local database, and discovery then reads that cache:

eth/watchers/serviceRegistryWatcher.go   // sees ServiceURIUpdate → store.UpdateOrch(…)
discovery/db_discovery.go                // store.SelectOrchs(…) → candidate orchestrators

So the chain is the source of truth, but nothing hits it on the hot path. A gateway picking an orchestrator for the next few seconds of video is reading its own local table.

CHAPTER 04 — THE TWO CLOCKS

Rounds are measured in Ethereum blocks, not Arbitrum ones.

Here's a thing I got slightly wrong in the earlier guides, and it's worth correcting properly because it changes what "a round is a day" means.

Livepeer runs on Arbitrum, where blocks arrive in a fraction of a second. If a round were 5,760 Arbitrum blocks it would last about half an hour. It doesn't — a round is 5,760 Ethereum L1 blocks. The node makes this explicit:

r.nextRoundStartL1Block = new(big.Int).Add(currentRoundStartL1Block, roundLength)
…
if r.tw.LastSeenL1Block().Cmp(r.nextRoundStartL1Block) < 0 { return nil }  // not yet

And the contract needs no special code for this, which is the neat part. RoundsManager.blockNum() just returns block.number — but on Arbitrum, block.number reports the L1 block number, not the L2 block height. The contract asks a simple question and the rollup answers in Ethereum time.

So: 5,760 Ethereum blocks. When the protocol was designed at ~15-second blocks that was a clean 24 hours. Since Ethereum moved to 12-second slots it's closer to 19–20 hours. "About a day" is still the right intuition; "exactly a day" was never quite true and is now clearly not.

Your devnet sidesteps the whole question. AdjustableRoundsManager.blockNum() returns a variable you can set, so a round costs one button press instead of most of a day.

Quick reference.

go-livepeer
The Go daemon orchestrators and gateways run. Moves video, signs tickets, and drives the on-chain calls your UI turned into buttons.
Arbitrum One
The layer-2 rollup the contracts are deployed to. Cheap and fast; posts its results down to Ethereum for security.
RPC endpoint
A server that lets you talk to a chain. A door into the network, not the place the protocol lives.
ServiceRegistry
The contract where an orchestrator publishes its network address. The bridge between an on-chain identity and a real machine.
abigen
Generates typed Go bindings from a contract ABI. How go-livepeer compiles against the protocol repo's exported interfaces.
L1 block
An Ethereum block. Rounds are counted in these — and on Arbitrum, block.number reports the L1 number, not the L2 one.
Round initializer
The part of go-livepeer that opens each new round. Sleeps a random delay first so orchestrators don't all pay gas for the same transaction.
Fork
A local chain seeded with a copy of real mainnet state. Between a blank devnet and the real thing.
